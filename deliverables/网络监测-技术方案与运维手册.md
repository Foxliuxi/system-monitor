## 二、技术方案

### 2.1 选型与理由

| 决策 | 选择 | 为什么不用替代方案 |
|------|------|-------------------|
| 运行时 | Python 3 + psutil | psutil 是跨平台系统指标的事实标准，本机已具备 |
| Web 框架 | **标准库 `http.server`** | 拒绝 FastAPI/uvicorn：单人运维工具，少一层依赖少一处故障点 |
| 实时推送 | **SSE** | 数据单向（服务端→浏览器），SSE 原生断线重连，代码量约为 WebSocket 的 1/3 |
| 图表 | **Canvas 自绘** | 拒绝 Chart.js CDN：断网即白屏，而且样式要跟主题严丝合缝 |
| 监听地址 | **仅 127.0.0.1** | 本机网络指标不应暴露给局域网任何设备 |
| 数据持久化 | 无（内存 30 分钟环形缓冲） | MVP 不需要时序库；接 InfluxDB 属二期 |

**整个项目的三方依赖只有一个：psutil。**

### 2.2 数据流

```
┌─────────────────┐   1s 周期   ┌──────────────┐
│ 采集线程         │────────────▶│ Sampler      │  psutil 差分 / netsh
│ (daemon)        │             │ (有状态)      │  首帧只建基线，速率返回 0
└────────┬────────┘             └──────────────┘
         │ 原始指标                    ▲ 只读最近一次探测结果（非阻塞）
         ▼                            │
┌─────────────────┐          ┌───────┴──────┐   1s/次 ping（最坏 4s）
│ Analyzer        │◀─────────│ Pinger 线程   │──▶ ok / timeout / error
│ 规则引擎 + 评分   │ 探测统计  │ + 尝试日志    │    自持 deque，统计从日志算
└────────┬────────┘          └──────────────┘
         │ {score, grade, items[], stats}
         ▼
┌─────────────────┐   version++  ┌──────────────┐  SSE    ┌────────────┐
│ Monitor 状态     │─────────────▶│ HTTP 线程     │────────▶│ 浏览器看板  │
│ latest + 环形历史 │  原子替换     │ /api/stream  │  1s     │ Canvas 绘制 │
└─────────────────┘              └──────────────┘         └────────────┘

┌─────────────────┐  2s: GPU / 进程排行    ┌──────────────┐
│ 慢采样线程        │  10s: 磁盘容量         │ SlowSampler  │
│ (daemon)        │  15s: 温度             │ 共享缓存      │──┐
└─────────────────┘                       └──────────────┘  │
                                                             ▼ 主循环每帧读取
                                                      （不阻塞 1s 节奏）
```

**为什么拆三个线程**：`nvidia-smi` 约 100ms、PowerShell 约 800ms、遍历进程约 30ms，
而单次 ping 最坏要吃满 4 秒超时窗口（DNS/TCP 各 1.5 秒）。这些塞进 1 秒主循环会把网络指标
采集节奏拖垮，出现"采样间隔忽长忽短"——那会让吞吐曲线的每秒速率全部失真。
更隐蔽的是：**丢包率的分母就是探测次数**，主循环被拖慢时分母也跟着失真，结论直接不可信。
所以慢指标与探测全部独立线程 + 共享缓存。

### 2.3 关键实现细节（踩过的坑）

**坑 1：`ipconfig` 取网关会拿到本机 IP。**
当接口同时存在 IPv6 链路本地网关时，`ipconfig` 把 IPv4 网关挤到续行，标签只出现一次。
正则只匹配到 `fe80::1234%21`，兜底逻辑"取第一个内网地址"于是抓到了本机 `192.168.0.200`。
**解决**：改读 `route print -4` 的默认路由行（`0.0.0.0 0.0.0.0 <gateway>`）。
这是本机实测踩出来的，不是理论问题。

**坑 2：命令输出编码顺序反了会静默乱码。**
GBK 与 UTF-8 的中文，用错误编码解码时 GBK 常常"解码成功但内容是乱码"。
**解决**：先严格 UTF-8，失败再退 GBK。顺序反了会把 UTF-8 中文解成乱码而"假装成功"。

**坑 3：断开的网卡 `LinkSpeed` 返回 0。**
用它判断"这块口值不值 1000 Mbps"会把千兆口误判成不可用，导致最重要的规则永不触发。
**解决**：从型号描述推断标称速率（GBE/Gigabit → 1000，Fast Ethernet → 100），
实测速率另存 `link_speed_mbps`，两者分离。

**坑 4：客户端断开连接会打印整页 traceback。**
浏览器刷新、关闭标签页都会触发 `ConnectionResetError`，socketserver 默认打印堆栈，
真实故障会被淹没。**解决**：重写 `handle_error`，识别连接类异常后静默。

**坑 5：JS 变量声明晚于使用（TDZ）。**
`rafPending` 声明在 `schedule()` 之后，靠"调用恰好发生在异步回调里"逃过报错。
这种靠时序巧合的代码会在重构时爆炸。**解决**：声明提前。

**坑 6：`psutil.process_iter()` + `cpu_percent()` 永远返回 0。**
psutil 的 `Process.cpu_percent()` 把"上次调用时刻"存在**实例属性**里，
而 `process_iter()` 每次返回**全新的 Process 对象**，导致每次都是首次调用 → 恒为 0.0。
网上大量示例代码都踩这个坑，表现为"进程 CPU 排行全是 0"。
**解决**：自己维护 `{pid: 累计CPU秒数}`，用两次采样的差值除以真实间隔，
再除以逻辑核数归一化（与任务管理器口径一致）。

**坑 7：`System Idle Process` 会霸占 CPU 排行第一名。**
它统计的是 CPU **空闲**时间，峰值能到 90% 以上。不过滤的话，用户想看真实应用，
结果第一名永远是它，真实应用被全部挤下去。
**解决**：按 pid（0/4）与进程名双重排除。

**坑 8：慢指标阻塞主循环会导致吞吐数据失真。**
`nvidia-smi` 100ms、PowerShell 800ms 如果放进 1 秒采样循环，
采样间隔会变成 1.1s / 1.8s 抖动，而吞吐速率是用"字节差 ÷ 真实间隔"算的，
间隔一抖，曲线全是毛刺。
**解决**：慢指标独立线程 + 各自周期 + 共享缓存。

**坑 9：超时窗口小于真实 RTT，会把"慢回包"全判成"丢包"（用户当场发现）。**
探测写的是 `ping -n 1 -w 900`，而本机公网 RTT 实测 **≈1000 ms**——
每一次包都回来了，只是比 900 ms 晚一点点，于是 90% 的探测被判超时，
界面报出 **90% 丢包**。同一时段用户用 `ping -n 10 www.baidu.com` 实测只有 **10%**。
**解决**：超时窗口改为 **4000 ms**（与 Windows `ping` 默认一致，保证与自己手测可比）。
教训：**超时窗口必须显著大于链路 P95 RTT，否则测出来的是超时率，不是丢包率。**

**坑 10：IPv6 回复行没有 `TTL=`，用它判断成功会 100% 误判。**
旧判断是 `if "TTL=" not in out: return None`。IPv4 回复是
`来自 223.5.5.5 的回复: 字节=32 时间=12ms TTL=65`，而 IPv6 回复是
`来自 2408:871a:... 的回复: 时间=1233ms`——**没有 TTL 字段**。
`www.baidu.com` 恰好解析到 IPv6，于是每一条成功回包都被当成失败。
**解决**：改看统计汇总行的 `已接收 = N` / `Received = N`（中英文、IPv4/IPv6 都有），
RTT 用 `(?:time|时间)\s*[=<]\s*(\d+)ms` 提取，兼容 `时间<1ms`。

**坑 11：把"发包失败"和"丢包"混成一个数。**
"Ping 请求找不到主机"、"传输失败。常见故障。"（无路由/ICMP 被拦）根本不是一个包发出去丢了，
但旧实现一律返回 `None`，与超时一起进丢包率的分子。
**解决**：探测结果三元化 —— `ok` / `timeout` / `error`。
丢包率 = `timeout ÷ 有效探测`，`error` 单独计数并在界面提示"丢包率无法取信"。

**坑 12：探测同步跑在采样循环里，本身就污染了统计。**
单次探测最坏吃满 4 秒超时，DNS/TCP 各 1.5 秒。放在 1 秒循环里同步执行，
采样周期被拖到 2-6 秒，而丢包率的分母恰恰是"探测次数"——分母失真，结论就不可信。
**解决**：探测独立线程（`collector.Pinger`），自持 `deque` 记录每次尝试的
状态与 RTT，统计直接从这条日志算；采样线程只读最近一次结果，永不阻塞。

**坑 13：曲线红点用"值为空"判断丢包。**
探测未完成、发包失败时值同样为空，于是图上会凭空多出红点，看着像丢包。
**解决**：历史点里显式记录 `gk`/`pk`（该次是否 `timeout`），红点只看这个标记。

### 2.4 系统监控的数据来源与可得性

| 指标 | 来源 | 权限要求 | 本机实测 |
|------|------|---------|---------|
| GPU 利用率 / 显存 / 温度 / 功耗 / 风扇 / 频率 | `nvidia-smi --query-gpu` | 无 | ✅ 全字段可用 |
| GPU 型号与显存总量 | `nvidia-smi` | 无 | ✅ 22528 MiB（**WMI 的 AdapterRAM 报 4GB 是 32 位溢出错误，不可用**） |
| 分区容量 | `psutil.disk_usage` | 无 | ✅ C/D/E 三个分区 |
| 物理盘型号与健康 | `Get-PhysicalDisk` | 无 | ✅ 3 块 SSD，全部 Healthy |
| 磁盘读写速率 | `psutil.disk_io_counters` 差分 | 无 | ✅ |
| **CPU / 主板 温度** | LibreHardwareMonitor HTTP `data.json` | 无（由 LHM 提权采集） | ✅ 实测 63.1 °C / 36.5 °C |
| **硬盘温度** | 同上 | 无 | ✅ 三块盘 45 / 45 / 30 °C |
| 温度兜底 | WMI `MSAcpi_ThermalZoneTemperature` | 管理员 | ❌ 本机 AMD 平台不暴露 |
| 进程 CPU / 内存排行 | `psutil.process_iter` + 自算差值 | 无（部分系统进程 `AccessDenied`） | ✅ 约 300 进程，耗时 ~30ms |

**温度这块的诚实结论**：
Windows 没有系统级通用温度接口。`psutil.sensors_temperatures()` 在 Windows 版**根本不存在**
（不是版本旧，是上游从未实现）。ACPI 热区在本机（AMD B550）不暴露，磁盘 SMART 需管理员。

最终方案是**接入 LibreHardwareMonitor 作为传感器后端**（详见 2.7），本工具只消费它的 HTTP 数据。
三路降级顺序：LHM → ACPI 热区 → 显示「不可用 + 原因」，**任何情况下都不编造数字**。

### 2.5 界面布局：系统在前，网络在后

**最终结构**（v1.2 起）：

```
顶栏 / KPI 七联
── 系统资源 ──  CPU|显卡  内存|硬盘  温度  进程监控
── 网络状态 ──  吞吐|延迟  链路
提醒条（折叠）
```

**为什么用两个独立 grid 而不是一个大 grid**：
分区标题（`系统资源 SYSTEM` / `网络状态 NETWORK`）需要横跨两列。
如果塞进同一个 grid 与 `grid-template-areas` 混用，自动布局会把标题挤进
areas 未占用的空位，结果不可控。拆成 `.g-sys` + `.g-net` 两个 grid、
中间用独立的标题行分隔，结构清晰且不会打架。

**目标场景**：1080×1920 竖屏副屏。原三列布局在这个宽度下会被压扁，内容只占 960px，
下方 40% 是空白——既浪费屏幕，又违背"一屏看全"的初衷。

**解决思路：让纵向空间按比例分配，而不是靠内容自然堆叠。**

```css
body { display: flex; flex-direction: column; }   /* 页面撑满视口 */
.main { flex: 1; display: flex; flex-direction: column; }
.g-sys { flex: 2.3 1 0; }   /* 系统区内容多，占更大比例 */
.g-net { flex: 1 1 0; }     /* 网络区内容少，压缩 */
.g-sys {
  grid-template-rows:
    minmax(150px, 1fr)   /* CPU + 显卡 */
    minmax(150px, 1fr)   /* 内存 + 硬盘 */
    auto;                /* 温度 */
    minmax(270px, 1.5fr) /* 进程排行 */
}
```

关键在两点：
1. **`fr` 让每行按比例吸收多余高度**，而不是全塞给图表（图表会被拉成瘦长条，难看）。
2. **`minmax` 下限兜底**，屏幕不够高时退回内容高度，页面可滚动。

配套细节：
- `.canvas-box { flex: 1 }` — 图表填满卡片剩余空间，Canvas 的 ResizeObserver 自动重绘。
- `.rank-list li { flex: 1 }` — 进程行均分高度。
  最初用 `justify-content: space-between`，结果行间距被扯得忽大忽小，很难看。
- `.foot { margin-top: auto }` — 脚注贴底，避免卡片拉高后内容全挤在顶部。

**"空一块"问题的根治**：同一行两张卡片高度必然相等，内容少的那张会留白。
内存卡只有「百分比 + 进度条」，被拉到与硬盘卡（三块分区）等高时空出 80px。
解决办法不是拉伸留白，而是**填入真实有用的信息**：已用 / 可用 / 当前占用最高的应用。
这条经验通用——**卡片留白应该用信息填，不是用间距填**。

**横屏必须单独一套行高。** 1080 高装不下这套布局（用 fr 会溢出被截断，
实测只能看到前 3 行）。所以 `@media (orientation: landscape) and (max-height: 1400px)`
里改成固定紧凑行高，并单独压缩硬盘（三块分区挤进 148px）与进程行（10 行挤进 212px）：

```css
.g-sys { flex: none; grid-template-rows: 126px 148px auto 212px; }
.g-net { flex: none; grid-template-rows: 112px auto; }
```

> 横屏的行高是算出来的，不是试出来的：先算所有固定块的总高，
> 再倒推剩下的空间能分给图表和进程表多少。改任何一处字号或内边距都要重算。

**提醒信息折叠**：分析列表是最长的内容（6-10 条、每条 3 段文字），展开会挤掉监控数据。
所以默认收起成一行，收起状态直接显示 `summary`（最该做的那件事），
点开才看完整因果链。数量统计（`2 项严重 · 3 项注意`）也放在收起条上，不展开也能判断严重程度。

**视觉方向**：系统区用蓝色系（`#38bdf8`）、网络区用紫色系（`#c084fc`）区分两大功能区；
大数字用 `font-weight: 300` 细字重配 `tabular-nums`，比粗体更精致；
卡片顶部加 1px 渐变高光营造层次；背景用三层径向渐变做微光晕，避免纯黑发死。

**验证方法（无头浏览器的坑）**：
Edge headless 与 SSE 长连接冲突 —— 页面永远等不到 load 完成，
加 `--virtual-time-budget` 会报 `Abnormal renderer termination`。
解决办法是生成一个**内联数据的静态快照页**，把 `EventSource` 换成立即返回数据的桩，
这样页面能正常"加载完成"，截图才稳定：

```js
window.fetch = async () => ({ json: async () => window.__SNAP__ });
window.EventSource = class { addEventListener() {} };
```

另外需要 `--in-process-gpu --disable-gpu-compositing`，否则本机 GPU 进程会崩
（`exit_code=-1073741819`）。

### 2.6 配色体系与主题切换

**起因**：副屏（1080×1920 竖屏）上暗色看不清。排查后确认不是"暗"的问题，是**层次没拉开**——
卡片底色 `#0b1219` 与页面底 `#06090e` 只差 4 级亮度，边框 `#1a2432` 在低端面板上等于不存在，
最小字 9.5px 用的 `#6a7c92` 对比度只有 4.1:1（WCAG AA 要求 4.5:1，小字更该高）。

**做法一：表面分三级，每级必须有可见亮度差。**

| 层 | 变量 | 暗色 | 亮色 |
|----|------|------|------|
| 页面 | `--bg` | `#0b1119` | `#e8eef6` |
| 卡片 | `--panel-top` / `--panel-bot` | `#182230` / `#131b26` | `#ffffff` / `#f6f9fd` |
| 卡内嵌块 | `--panel-2` | `#1d2836` | `#eef3fa` |
| 底槽 | `--track` | `#222f3e` | `#dde6f1` |
| 边框 | `--line` | `#35485f` | `#b9c9da` |
| 次要文字 | `--muted` | `#93a6bb`（≈7:1） | `#55697f`（≈5.4:1） |

**做法二：所有颜色一律令牌化，不留硬编码。**
原来散落 40 余处 `#151f2b`、`rgba(10,17,24,.75)`、`rgba(255,255,255,.012)` 这类裸色值，
换主题就得逐行改、必漏。现在统一到 `--track / --zebra / --hairline / --c-good / --bd-warn`
这类语义变量，切换主题只是换一份变量表：

```css
:root                     { --bg: #0b1119; --text: #f4f8fd; ... }  /* 暗色默认 */
html[data-theme="light"]  { --bg: #e8eef6; --text: #0d1927; ... }  /* 亮色覆盖 */
```

**做法三：Canvas 图表不能只改 CSS。**
曲线、面积渐变、丢包红点、排行占比条都是画在 canvas / 内联 style 上的，CSS 变量管不到。
所以 `app.js` 里 `COL` 对象在每次绘制前从 `getComputedStyle` 读 `--blue / --chart-grid`
这类变量：

```js
const COL = { ... };
function readTheme() {
  const cs = getComputedStyle(document.documentElement);
  COL.grid = cs.getPropertyValue('--chart-grid').trim() || COL.grid;
  ...
}
```
图表序列只存语义键（`ckey: 'blue'`），颜色在 `draw()` 里解析——主题一换，下一帧自动是新色。
排行占比条是内联 style，靠清空渲染签名 `_sig.rank` 触发重绘。

**两个必须注意的细节**：
1. **首屏闪烁**：亮色用户在 HTML 解析到 `<body>` 前会先看到一瞬暗底。
   在 `<head>` 里放一段极小内联脚本，从 `localStorage` 读出主题先设上，再加载样式表。
2. **`localStorage` 可能抛异常**（隐私模式 / 部分企业策略），读写一律包 `try`，
   失败只是不记忆选择，不影响功能。

切换入口在顶栏右上角两格控件（`data-theme-set="dark|light"`），选择写入
`localStorage['smon.theme']`。

### 2.7 传感器后端：LibreHardwareMonitor 集成

**为什么必须借外力**：CPU 温度要靠内核驱动读 SMN/MSR，这是所有监控软件的共同前提。
自研驱动要签名、要过杀软，成本远超收益。所以选 LHM 做传感器后端，本工具做消费方。

**安装与校验**（已在本机完成）：

| 项 | 值 |
|----|-----|
| 版本 | v0.9.6（2026-02-14） |
| 位置 | `C:\Tools\LibreHardwareMonitor` |
| 下载 | GitHub 直连被阻断，走 `ghproxy.net` 镜像 |
| 校验 | SHA256 `086d9f1b…c529c001`，与官方 release 元数据逐位一致 |
| 依赖 | PawnIO 内核驱动（首次运行自动安装，服务名 `PawnIO`） |
| 数据接口 | `http://127.0.0.1:8085/data.json` |

**为什么不用 WMI Provider**：0.9.6 已移除该功能（源码 `MainForm.cs` 中已无 WMI 相关设置项），
改用内置 HTTP 服务。`/metrics` 是 Prometheus 格式，`/data.json` 是传感器树，这里用后者——
带传感器名字，便于按名字选值。

**踩坑 1（我判断错过一次，记录在此以免重犯）：设置文件不是 `.exe.config`。**

LHM 用 `Path.ChangeExtension(Application.ExecutablePath, ".config")` 定位设置文件。
`ChangeExtension` 是**替换**最后一个扩展名，所以 `LibreHardwareMonitor.exe` → `.config`
得到的是 **`LibreHardwareMonitor.config`**，而不是 `.exe.config`。

我最初把 `appSettings` 写进了 `.exe.config`（那是 .NET Framework 的运行时配置），
然后观察到几轮"启动后 25–30 秒自行退出"，就得出"配置里开服务会崩"的结论——
**这个结论是错的**。修正过程：翻目录发现 63 KB 的 `LibreHardwareMonitor.config`，
里面 `runWebServerMenuItem` 早就是 `true`（用户从菜单勾选后保存的），
带这份配置启动，15 秒后监听正常建立、`data.json` 返回 200。

**正确结论**：把 `runWebServerMenuItem=true` 写进 `LibreHardwareMonitor.config`，
LHM 启动后可自动开服务，**不需要每次去点托盘菜单**。
那几次"自退"的真实原因未能复现（叠加了多实例、首次装驱动、以及我这边派生进程
在命令结束时被回收等因素），不作为结论写进文档。

**踩坑 2：`SO_REUSEADDR` 让端口冲突变成静默故障（本工具自身的问题）。**
服务端原来用 `ThreadingHTTPServer` 默认的 `allow_reuse_address = True`，并且 `pick_port`
的探测 socket 也开了 `SO_REUSEADDR`。Windows 下这意味着**两个进程能绑同一端口**：
新实例"启动成功"，但请求全部由老实例接走——于是改完代码、重启程序，
看到的还是旧界面，还查不出原因（本次用户遇到的正是这个）。
**修法**：`QuietServer.allow_reuse_address = False`，探测 socket 加
`SO_EXCLUSIVEADDRUSE`，与真实绑定同口径；端口被占就 `bind` 失败并顺延到下一个，
行为可预期。日志里现在会明确打出自增后的实际端口。

**踩坑 3：`data.json` 的真实层级比文档多一层。**
实际是 `Sensor → 机器名(FOX-01) → 硬件 → 分组 → 传感器`。按固定层级解析会一个都取不到，
改成递归 + 用 `ImageURL`（`cpu.png` / `mainboard.png` / `hdd.png`）判定硬件类型——
比按型号名匹配可靠，因为 `ASUS PRIME B550M-K` 这种名字里根本没有 board 字样。

**踩坑 4：叶子节点的 `Children` 是空数组而不是 `null`。**
`if ch.get("Children") is None` 会把所有传感器都判成非叶子，导致整棵树收不到值。

**踩坑 5：阈值混在读数里。**
NVMe 会同时报 `Composite Temperature 45 °C` 和 `Warning Temperature 89 °C`，后者是告警阈值。
不加过滤直接取最大值，界面就会显示 89 °C 的假高温。现在按名字排除
`warning|critical|max|min|limit`，硬盘优先取 `Composite Temperature`，并过滤 `0 °C` 的空型号设备。

**性能**：一次 HTTP 拿全部传感器约 30 ms，比逐个跑 PowerShell（每次 1–2 秒）便宜两个数量级，
所以 LHM 可用时 `_cpu_temp()` 的 PowerShell 路径完全不执行。温度按 15 秒周期采样。

## 三、评分口径（可复核）

总分 100，扣分后归零截断。

**分级扣分（每条规则命中即扣）**
- `critical` 严重：−18 分
- `warn` 注意：−8 分

**质量指标额外扣分**（比"配置不够好"更影响体感，所以单独加权）

| 指标 | 扣分公式 | 上限 |
|------|---------|------|
| 公网丢包率 | `loss% × 4` | 20 |
| 抖动 > 40 ms | `(jitter − 40) / 4` | 12 |
| 公网延迟 > 30 ms | `(rtt − 30) / 6` | 15 |

**等级**：≥85 优秀 ｜ 70-84 良好 ｜ 50-69 一般 ｜ <50 较差

> 口径说明：
> - 网络畅通时 84 分 = 100 − 8（2.4GHz）− 8（千兆口空置）；延迟 18-24 ms、抖动低、零丢包，质量项几乎不扣分。
> - 拥堵时段 41-49 分，主要来自延迟项（`(1161−30)/6` 触顶 15 分）、抖动项与丢包项——此时扣分是**真实的体感反映**。
> - **评分是相对的**：同一套口径下比较才有意义，不要跨环境比绝对分。

| D | 内存压力大 | mem ≥ 90% | warn |
| E 端到端 | 到网关就丢包 | 网关丢包率 > 0 | critical |

## 五、部署与运维

### 5.1 启动

```bash
双击 run.bat                        # 推荐，自动开浏览器
python server.py                    # 默认 8770，端口占用自动 +1 递增
python server.py --quiet            # 只输出警告与错误
python server.py --ping-target 1.1.1.1   # 海外网络改探测目标
```

首次启动约 2 秒（采集硬件画像，含 2 次 PowerShell 查询），之后 1 秒一个采样点。
进程排行在启动后约 1 秒出第一份数据（首轮只建 CPU 时间基线）。

**想读 CPU / 硬盘温度，必须以管理员身份运行**：右键 `run.bat` → 以管理员身份运行。
显卡温度不需要管理员。普通权限下这两项会显示「不可用 + 需要管理员权限」，
程序不会因此崩溃或降级其他功能。

### 5.2 资源占用（实测）

| 项 | 实测值 |
|----|--------|
| 内存（工作集） | **39.1 MB** |
| CPU（折算到全核） | 约 **0.7%**（单核约 11%，16 线程摊薄） |
| 磁盘 | 不写盘 |
| 网络 | 每秒 1 ICMP + 1 DNS 查询 + 1 TCP 握手（合计约 3 KB/s） |

**开销明细**（这段实测值得记住，它决定了各指标的采样周期）：

| 采集项 | 单次耗时 | 周期 | 占单核 |
|--------|---------|------|--------|
| 进程遍历（339 个进程） | **344 ms** | 5 秒 | 6.9% |
| `nvidia-smi` | 73 ms | 2 秒 | 3.6% |
| 磁盘分区/IO | 约 1 ms | 2 秒 | ~0% |
| 温度（PowerShell） | 约 800 ms | 15 秒 | 子进程开销，父进程仅等待 |
| 网络主循环（psutil + ping） | 约 20 ms | 1 秒 | 2% |

> 进程遍历是最大开销：`OpenProcess` 对每个进程约 1ms，339 个进程就是 344ms，
> 这是 Windows 的固有成本，没有批量接口可绕。所以进程排行定在 **5 秒**一次——
> 排行不是秒级指标，用 2 秒换 3 倍 CPU 开销不划算。
> 如果用 2 秒周期，单核会被吃掉 17%，一个监控工具自己变成负载就没有意义了。

### 5.3 故障排查

| 现象 | 原因 | 处理 |
|------|------|------|
| 页面打开空白 | 端口被占 / 服务未起 | 看控制台输出的实际 URL |
| 一直"连接断开，重试中" | SSE 被拦截 | 检查是否装了拦截插件；换浏览器 |
| 延迟全是 `--` | 网络禁 ICMP | 改 `--ping-target`，或看 DNS/TCP 两项 |
| WiFi 一栏为空 | 有线连接 / `netsh` 被策略禁用 | 正常现象（有线时无此栏） |
| 网卡清单为空 | PowerShell 被执行策略拦住 | 需允许 `Get-NetAdapter` 运行 |
| **CPU / 硬盘温度显示不可用** | 非管理员，或主板不暴露 ACPI 热区 | 右键 `run.bat` → 以管理员身份运行；仍不行就装 LibreHardwareMonitor |
| **显卡卡片显示不可用** | 非 NVIDIA / 无 `nvidia-smi` / 驱动异常 | 卡片里会写明具体原因（AMD/Intel 无公开接口） |
| **进程排行一直是 0%** | 首次采样只建基线 | 等 1 秒自动补齐；持续为 0 说明 PID 复用异常，重开程序 |
| 进程排行少了很多进程 | 系统进程 `AccessDenied` | 正常，普通权限读不到受保护进程 |
| 评分一直不变 | 分析项无变化（信号/频段不会实时变） | 正常，只有指标类规则会实时波动 |

## 七、边界声明

- 本工具只做**观测与提示**，不修改任何系统设置。所有优化动作需你手动执行。
- 评分与阈值是**经验区间**，用于同一台机器的纵向对比，不是行业标准。
- 硬件型号推断依据 `Get-NetAdapter` 的描述字符串，非标准命名可能识别不准。
- 仅 Windows 完整可用；采集核心跨平台，分析引擎的硬件推断为 Windows 专用。
- **温度数据依赖第三方工具 LibreHardwareMonitor 常驻运行**（已安装于 `C:\Tools\LibreHardwareMonitor`）。
  它是本工具唯一的运行时外部依赖，且必须提权（读内核驱动）。LHM 不在时温度回退到 ACPI，
  再读不到就如实标不可用。
- **本工具自身不以管理员运行**，也不需要：所有需要特权的采集都交给 LHM。
